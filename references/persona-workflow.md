# 客户人格工作流

## 1. 输入登记

建立只含元数据的登记表：

```text
customer_id: 非真实姓名的短代号
chat_path: 原始聊天在 private_data 中的路径
persona_speaker: 客户本人的精确说话人标签
conversation_partner: 对话对象标签及关系
addressing: 玩偶称呼对方的方式
desired_tone: 温柔/活泼/克制/幽默等
desired_care: 关心方式和主动程度
desired_length: 简短/中等/详细，或句数与字数
required_patterns: 必须出现的回复习惯
forbidden_patterns: 禁止称呼、主题和表达
voice_mode: 系统音色/已授权个人音色 URI/暂不配置
authorized_stage: 本轮授权边界
```

不要把聊天正文、API Key、Wi-Fi 密码、真实姓名或录音内容写入登记表。

## 2. 说话人确认

先本地解析聊天并仅输出参与者标签、消息条数、可解析率、文件哈希和时间范围。`persona_speaker` 必须与其中一个标签精确一致。

- 风格统计集合：`message.speaker == persona_speaker`。
- 场景上下文：该消息前最近一条其他说话人的消息。
- 不把对方的口头禅、句长和语气词混入目标人格。
- 多人聊天或混合导出不能自动套用双人分析器；先按用户指定范围拆分，且不跨客户合并。

## 3. 生成候选

优先复用母版命令：

```powershell
python -m desktop_tool.ai_doll_tool.cli analyze-chat `
  --input "<private-chat-path>" `
  --owner "<exact-persona-speaker>" `
  --output "<private-output-directory>"
```

候选必须经过敏感内容过滤和人工复核。不要因为高频就学习以下内容：

- 密码、验证码、账号、身份证、银行卡、详细地址、医疗隐私。
- 第三人的姓名、关系冲突、私人经历和评价。
- 一次性争吵气话、威胁、孤立、贬低、控制或违法建议。
- 对现实人物的承诺，例如“我已经替你做了”“现实中的我正在说话”。

## 4. 合并客户希望

用户明确提出的目标回复效果是最高优先级。以三层规则合并：

1. 身份和隐私硬约束。
2. 用户本次明确要求与禁用项。
3. 聊天中稳定、无害且有代表性的表达习惯。

把第二层与第三层不一致处列为“主动定制”，例如聊天原本短句较多，但用户明确要求回复更详细。不要把这种变化错误描述为“从聊天中分析得到”。

## 5. 审批预览

审批预览应包含：

- 目标说话人标签和纳入/排除消息数量。
- 3 至 8 条核心人格规则。
- 常用称呼、语气词、句长、标点和幽默程度。
- 安慰、鼓励、道歉、庆祝、普通日常和不知道事实时的策略。
- 用户要求的主动定制项。
- 禁止称呼、禁止主题和不可模仿表达。
- 6 至 12 个脱敏场景示例；示例可改写，但要保留目标风格。
- AI 身份说明。

在用户明确说“人格/回复风格通过”前，不写入设备公共配置，也不提前索取或处理“我在”录音、不构建、不识别或烧录设备。风格通过后结束第一步，提示用户第二步只需提供本人或已授权的短“我在”录音；录音处理按 wake-ack-audio.md 执行。

## 6. 设备配置映射

- `persona.summary`：角色关系、身份说明、关心原则和重要定制项，保持短小。
- `persona.reply_style`：句长、称呼、语气词、主动提问、回复丰富度和禁用表达。
- `style_examples`：只收录批准示例；每项给短场景文本和 1 至 12 个关键词。
- `memories`：只收录用户明确确认且适合设备长期保存的关系事实；默认不从聊天自动写入。
- `blocked_topics`：短关键词列表；医疗、财务、违法等高风险问题同时在提示词要求寻求专业帮助。

原始聊天不编译、不压缩、不嵌入固件。人格公共配置中也不得出现 API Key、密码、音色 URI 或可识别第三人的隐私。

## 7. 离线验收

至少生成以下五类预览：

1. 对方说累或难过。
2. 对方分享开心的事。
3. 对方需要鼓励。
4. AI 需要道歉或承认不知道。
5. 用户要求禁用的称呼或主题被触发。

逐项检查称呼、温柔度、关心程度、长度和主动定制项。只展示脱敏问题与回答，不展示原始聊天上下文。
