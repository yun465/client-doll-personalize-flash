# 客户玩偶个性化与烧录

把当前已验收玩偶工程作为母版，为一位客户生成独立的人格配置、固件工作副本和可验证烧录结果。原始聊天、录音、Wi-Fi、API Key、音色 URI 和 Flash 备份始终留在私有目录，不进入 Git、Skill 或交付固件的人格明文之外。

## 开始前

1. 若目标项目根目录存在 `AGENTS.md` 或 `PLAN.md`，读取并遵守；缺少其中任一文件不是错误，改用本 Skill 的内置项目基线继续。只有进入构建或烧录阶段时，才需要读取母版工程的最新门禁文件。
2. 默认项目布局由用户或项目配置提供：客户工作区、客户软件目录和已验收母版必须使用当前机器上的实际路径；不要把本机路径写入公开产物。
3. 若用户给出其他路径，以用户明确路径为准。不要把母版中的 `private_data/`、构建目录、Flash 备份或密钥复制到客户项目。
4. 读取 [current-project-baseline.md](references/current-project-baseline.md)，只复用已经验证的架构与硬件接口；仅做聊天分析时不依赖母版目录可访问。不要把某一块旧板的 COM 号、MAC、NVS 或个人音色当作新板默认值。
5. 明确当前阶段：仅分析、生成预览、准备工作副本、离线构建、真机烧录、写入配置或付费对话测试。一次只完成已获授权的阶段。
## Windows 本地命令恢复

本机默认沙箱偶发无法启动 PowerShell。若命令返回 `helper_unknown_error`、`setup refresh had errors`、`CreateProcess ... Rejected` 或同类“命令进程未启动”错误：

1. 把它判断为运行环境故障，不是 Skill、聊天文件或项目不存在的证据。
2. 不要重复普通模式，也不要让用户发送“继续重来”。立即把同一条最小、只读命令用 `require_escalated` 受控重试一次，并在工具批准说明中写明是只读恢复。
3. 恢复后用 `Get-Location`、`Test-Path -LiteralPath` 和 `Get-Item -LiteralPath` 核对精确路径，再继续当前阶段。包含空格或中文的路径始终使用 `-LiteralPath`。
4. 处理聊天时调用本地分析器，让它只输出标签、数量和私有产物路径；不要用终端直接打印聊天全文。
5. 若受控重试也无法启动，保留两次原始错误并停止。只报告“运行时仍不可用”，不得声称 Skill 或聊天文件不存在，除非 `Test-Path` 已实际返回 `False`。

这一次只读恢复不扩大对聊天、联网、烧录或付费操作的授权。

## 固定两步客户流程

这是本 Skill 的默认交互顺序，不合并、不提前索取第二步材料：

1. **聊天与回复风格验收**：用户先提供聊天记录、明确“客户本人”标签、对话对象和希望的回复效果。只进行本地分析、脱敏人格预览和离线回答预览。用户明确确认“回答风格通过”前，不处理录音、不构建、不识别或烧录设备。
2. **本地“我在”录音与烧录**：人格通过后，用户再提供本人或已获明确授权的短录音。该录音仅用于“小酥肉”唤醒后本地播放“我在”，不等于云端个人 TTS 音色。按 [wake-ack-audio.md](references/wake-ack-audio.md) 在本地检查 M4A/WAV/MP3/AAC 等格式、裁为语音前后各约 0.1 秒静音、转换为 16 kHz/单声道/16-bit PCM，运行测试并构建。然后重新识别目标板；只有用户已经明确指定该板及完整烧录或最小更新范围时才写入，否则先展示身份和拟写分区等待确认。

第二步默认不上传录音、不创建云端音色、不调用 ASR、DeepSeek 或 TTS。录音变化只会改变应用镜像；已有客户板通常只需更新应用分区并保留 NVS、双 LittleFS 和模型。新板仍需按完整性分类决定是否完整烧录。
## 必需输入

调用时至少确认以下信息；用户已提供的不要重复询问：

- 聊天记录的精确文件路径。
- 哪个说话人标签是“客户本人/目标表达风格来源”。
- 对话对象是谁，以及玩偶应如何称呼对方。
- 客户希望的回复效果：温柔程度、关心程度、长度、幽默、语气词、表情、主动提问、常用称呼和明确禁用内容。
- 本轮允许做到哪一步。
- 若要烧录：目标板串口、芯片/Flash/PSRAM 身份，以及这是新板还是已有客户板。
- 若使用本地“我在”：声音权利人、明确授权说明、录音精确路径；录音内容应只有自然说出的“我在”。
- 若另行使用云端个人音色：声音权利人、授权说明和是否已取得音色 URI；不得把本地“我在”录音自动当成声音克隆授权。

若聊天记录无法稳定区分说话人，先只报告识别到的标签和消息数量，等待用户指定；不得猜测“客户本人”。

## 工作流

### 1. 建立客户隔离区

- 每位客户使用独立目录，例如 `client\software\customers\<customer-id>\`。
- 原始聊天与录音只放在该工作副本的 `private_data/`；确保 Git 忽略后再处理。
- 若当前客户的源码工作副本尚不存在，从母版的受版本控制文件创建干净副本。不要用 `client\software` 是否完全为空作为判断，因为其中可以已有 `skills` 或说明文件。优先 `git archive` 或逐个复制 `git ls-files`，不得整目录复制构建缓存和私有内容。
- 记录母版提交哈希、目标客户代号和生成时间；不要记录真实姓名、聊天正文或密钥。

### 2. 分析聊天并生成候选人格

按 [persona-workflow.md](references/persona-workflow.md) 执行。

- 只用用户明确指定的“客户本人”消息推断措辞、句长、语气词、关心方式和回复习惯。
- 对方消息仅用于理解触发场景和关系语境，不学习对方的表达风格。
- 用户本次明确提出的“希望如何回复”高于聊天统计；把偏离原聊天的地方标为主动定制项。
- 排除密码、验证码、账号、住址、医疗隐私、第三人隐私、争吵气话和控制/贬低表达。
- 不把原始聊天全文写入固件；只生成短人格摘要、少量经批准的场景示例、确认记忆和禁用主题。
- 玩偶必须说明自己是按该客户表达习惯设计的 AI 角色，不能声称现实中的本人正在实时回复。

输出一份不含原始聊天正文的审批预览，至少包含：目标说话人、纳入/排除数量、常用称呼、语气与长度、关心策略、主动定制项、禁用规则、6 至 12 个候选场景示例。没有用户确认，不进入集成。

### 3. 编译和集成人格

- 复用母版 `desktop_tool/ai_doll_tool` 的聊天导入、风格分析、敏感信息过滤和人格包编译代码；不要另写一套平行实现。
- 用 `analyze-chat --owner <精确标签>` 做本地分析。所有示例默认未批准；只集成用户批准或用户明确提供的示例。
- 将批准结果编译为设备端公共配置结构：`persona.summary`、`persona.reply_style`、`style_examples[]`、`memories[]`、`blocked_topics[]`。
- 公共配置写入 LittleFS A/B 或通过现有 `set_public_config` 通道写入；API Key、Wi-Fi 密码和音色 URI 只进入独立 NVS 配置流程。
- 集成后先运行人格包、提示词、敏感信息和固件配置合同测试。生成至少 5 个离线回答预览，覆盖日常、安慰、开心、道歉和未知事实。
- 向用户展示预览并请求人格验收。未通过时只调整人格数据，除非证据表明固件接口有缺陷。

### 4. 构建

按 [firmware-and-flash.md](references/firmware-and-flash.md) 执行。

- 使用 ESP-IDF 6.0.2 和项目锁定依赖；先运行相关定向测试，再做完整构建。
- 保持当前录音端点基线：ESP-SR VAD 使用 30 ms 帧、约 120 ms 连续语音确认起声、起声后 810 ms 静音自动停录、3 秒未起声取消、最长 5 秒；VAD 初始化失败时退回最长 5 秒。
- 本地“我在”必须在播放结束后清空麦克风 DMA，再开始 VAD 录音；设备音量 100% 继续使用 180% 饱和限幅增益。
- 构建确认目标为 ESP32-S3 N16R8、Octal PSRAM、当前唤醒模型 `wn9_xiaosurou_tts2`。
- 当前已验收音频基线是：设备音量 100% 对应 180% 饱和限幅 PCM 增益；有效 WAV 完整下载到 PSRAM 后再播放；I2S 短写必须循环补齐。除非客户明确要求调整，不得退回边下载边播放或单次 I2S 写入。
- 构建日志不得包含聊天正文、API Key、Wi-Fi 密码、音色 URI 或录音内容。应用镜像会嵌入本地“我在”PCM，因此该镜像和哈希清单必须作为客户私有产物保存，不放公共 outputs、不跨客户复用。
- 报告应用大小、分区余量、镜像 SHA-256、测试结果和未完成风险；然后等待烧录授权。

### 5. 烧录与验证

- 烧录前重新枚举串口并读取芯片身份、MAC、Flash 大小和 PSRAM；让用户确认目标板。
- 在决定“完整烧录”还是“最小更新”前，必须按 [firmware-and-flash.md](references/firmware-and-flash.md) 对 Bootloader、分区表、OTA 数据、应用、双 LittleFS 和模型做只读完整性分类。历史 MAC、旧烧录记录或应用可写入都不能证明基础分区完整。
- 新板可在明确授权后擦除厂家测试固件并完整烧录。已有客户板默认只写必要分区，保留 NVS、LittleFS、模型和其他客户数据；若本次正要更新人格分区，明确列出将覆盖的分区。
- 使用构建目录生成的 `flash_args`，逐段写入并验证哈希。不得硬编码旧 COM3、旧 MAC 或旧镜像路径。
- 本项目明确不启用 Flash 加密、NVS 加密或 Secure Boot。禁止烧写相关 eFuse，也禁止宣称“捡到后无法读取”；只能说明物理接触者可能提取固件与配置。
- 烧录后依次验证启动、16 MB Flash、8 MB Octal PSRAM、`小酥肉` 模型、配网入口和人格加载状态。
- 启动验证只能使用不会自动发送对话命令的串口监视方式；不得调用会顺带执行 `test_dialog_once` 的旧脚本。
- 真实对话前只查询 Wi-Fi、DeepSeek、硅基流动和个人音色配置的“存在/不存在”布尔状态，不读取或打印秘密值。缺少任何必需配置时，让用户通过手机本地网页补齐。
- 到达真实 ASR、DeepSeek 或 TTS 前停止。只有用户对本次真实网络/可能付费测试另行明确批准，才执行一次受限对话并报告调用次数。

## 完成标准

最终交付必须说明：

- 客户工作副本与人格产物位置。
- 目标说话人标签及仅用其消息学习风格的证明性统计。
- 用户明确要求如何覆盖聊天推断。
- 离线预览、人格验收、录音格式与授权、最终 PCM 时长/首尾静音/哈希、测试和构建结果。
- 若已烧录：端口、设备身份、写入分区、镜像哈希和启动验证。
- 哪些操作未执行，尤其是真实 API 调用、个人音色上传和 eFuse。
- 原始聊天、录音、密钥、音色 URI 未进入 Git 或 Skill。

不要因为用户说“继续”就跨越尚未批准的付费调用、录音上传、真实配置写入或真机烧录门禁。
